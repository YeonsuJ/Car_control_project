# CAN 통신 확장성 문제 해결

## 문제점: 경직된 1:1 통신 구조의 한계
초기 CAN 통신 시스템은 각 노드(제어기)가 주고받을 메시지 ID를 1:1로 미리 약속하는 방식으로 설계했다. 예를 들어, 'A' 노드는 ID 0x100을 'B' 노드에게만 보내고, 'B' 노드는 오직 그 ID만 수신하도록 설정하는 방식이었다. 이 구조는 소수의 노드가 정해진 데이터만 교환할 때는 단순하고 명확했다.

하지만 시스템에 새로운 기능이 추가되면서 문제가 발생했다. 가령, 새로운 센서 'C'가 추가되어 자신의 데이터를 'A'와 'B'에게 보내야 할 경우, 'A'와 'B' 노드 모두 'C'의 ID를 수신하도록 코드를 수정하고 펌웨어를 업데이트해야만 했다. 기능 하나를 추가할 때마다 관련된 모든 노드의 ID 테이블을 일일이 수정하고 배포하는 과정은 시스템의 확장성과 유지보수성을 심각하게 저해하는 원인이 되었다.


## 해결 방안: 브로드캐스트와 하드웨어 필터링의 조화
이러한 비효율을 해결하기 위해 통신 아키텍처를 완전히 변경했다. 새로운 방식은 특정 노드를 지정해서 보내는 것이 아니라, **모든 노드가 자신의 데이터를 일단 버스에 전부 브로드캐스트(broadcast)**하는 것이다. 즉, 각 노드는 "내 데이터는 이것이니 필요한 사람은 가져다 써라"라는 식으로 정보를 공유한다.

물론 이 방식은 버스에 많은 트래픽을 유발하지만, CAN 컨트롤러가 가진 강력한 하드웨어 필터링 기능을 활용하여 문제를 해결했다. 각 노드는 이제 자신이 수신해야 할 메시지 ID 목록을 하드웨어 필터에 미리 설정해 둔다. 그 결과, 버스에 수많은 메시지가 오가더라도 자신의 MCU는 오직 필터에 등록된 ID의 메시지만 선별적으로 수신하여 처리한다. 자신과 관련 없는 나머지 메시지들은 하드웨어 수준에서 무시되므로 CPU에 전혀 부하를 주지 않는다.

이러한 방식으로 변경한 결과, 새로운 노드나 데이터 종류가 추가되더라도 기존 노드들의 코드를 수정할 필요가 완전히 사라졌다. 필요한 데이터를 수신할 노드만 자신의 필터 설정을 변경하면 되므로, 시스템은 매우 유연하고 확장성이 뛰어난 구조를 갖추게 되었다.
